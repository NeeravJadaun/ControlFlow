# Security and Limitations

## This is a portfolio/demo project

ControlFlow is a demonstration of platform-engineering patterns (workflow
engines, audit trails, RBAC, idempotent scheduled jobs, dashboard/drilldown
consistency). **It has not had a security audit and is not production
software.** Do not point it at real personal data, real financial accounts,
or a real compliance program.

## The financial-operations workspace is educational only

The FATCA/CRS/QI classification logic (`backend/app/services/
classification.py`) is a deliberately simplified rule set operating on a
handful of synthetic entity attributes (`us_person`, `entity_type`,
`tax_residency_country`, `qi_agreement_on_file`). It does **not** implement
the actual regulations, does not handle the many real-world edge cases
(treaty elections, look-through entities, documentation curing periods,
multi-jurisdictional dual status, etc.), and must never be used to make a
real classification decision. Every page in the financial workspace
displays this disclaimer in the UI, not just in documentation. The same
applies to the simplified W-8/W-9 completeness and renewal-period modeling.

## Authentication and authorization

- Passwords are hashed with bcrypt (`passlib`); plaintext passwords are never
  stored or logged.
- Sessions are stateless JWTs (HS256), signed with `SECRET_KEY`, sent as a
  `Bearer` token and validated on every request via a FastAPI dependency.
  The demo `SECRET_KEY` in `.env.example` is intentionally a placeholder —
  **rotate it before any use beyond local demo.**
- The frontend stores the JWT in `localStorage`. This is a conscious
  trade-off for a demo SPA (simpler than cookie + CSRF-token plumbing) but
  is more vulnerable to XSS token theft than an httpOnly cookie would be. A
  production system should use httpOnly, SameSite cookies instead.
- Five roles (Operations Analyst, Reviewer, Compliance Officer, Auditor,
  Admin) are enforced **server-side** on every sensitive endpoint via
  `require_roles(...)` — the frontend hiding a button is a UX nicety, not
  the security boundary. Admin bypasses role checks everywhere (including
  workflow-transition role requirements), which is appropriate for a small
  demo but would need scoping down (break-glass audit logging, narrower
  admin powers) in a real deployment.
- No MFA, no SSO/OIDC integration, no password-reset flow, no account
  lockout after repeated failed logins. All would be required before any
  real-world use.

## Optimistic locking

Entities, documents, and cases carry a `version` integer. Updates that
matter (entity edits, document approve/reject, case edits/resolve) require
the caller to supply the version they last read; a mismatch returns 409
Conflict rather than silently overwriting a concurrent change. This is
enforced at the application layer (checked explicitly in each route,
mirroring SQLAlchemy's own `version_id_col` mechanism which is configured on
the ORM models) — see `backend/app/api/routes/entities.py::update_entity`
for the pattern. `User` rows do not use optimistic locking (no concurrent
multi-actor editing scenario for user profiles in this demo).

## Audit trail

Every mutating action writes an `AuditLog` row (actor, timestamp, entity,
action, before/after JSON, correlation ID) in the same database transaction
as the change itself, so an audit entry and its corresponding change either
both commit or neither does. Nothing in the codebase updates or deletes an
`AuditLog` or `WorkflowEvent` row — they are structurally append-only (no
`PATCH`/`DELETE` route exists for either table). This is enforced by
convention and by the absence of such routes, not by a database-level
`REVOKE UPDATE` — a real deployment should add that as defense in depth.

## Logging

Structured JSON logs on stdout include: correlation ID, HTTP method/path/
status/duration, and (for domain log lines) entity types and IDs. They never
include request/response bodies, passwords, tokens, or field-level personal
data. See `backend/app/core/logging.py` and `backend/app/main.py`'s request
middleware.

## Data handling

- All data is synthetic, generated by `backend/app/seed/seed.py` with
  `Faker` under a fixed RNG seed. No real names, emails, tax IDs, or account
  numbers exist anywhere in this codebase or its seed output.
- Document and case attachments store **metadata only**
  (filename, content type, size, a reference string) — no binary file
  content is uploaded, stored, or served anywhere in this demo.
- `sample_data/` contains only the seed-run summary JSON
  (`demo_scenarios.json`), not user data.

## Known limitations

- **No multi-tenant isolation.** The schema is industry-neutral and could
  support multiple workspaces, but the demo ships a single, shared
  financial-operations workspace — there's no `workspace_id` scoping layer.
- **No file storage backend.** Real document/attachment upload would need
  object storage (S3-compatible) plus virus scanning and access-controlled
  URLs; this demo deliberately stays metadata-only to avoid handling
  arbitrary binary uploads without that infrastructure.
- **Single-region, single-instance assumptions.** No read replicas, no
  multi-region failover, no queue-based outbox pattern for the audit log —
  fine for a demo, not for a real regulated workload.
- **CSV import is best-effort.** Bad rows are reported back (row number +
  error) but the whole import isn't wrapped in a single all-or-nothing
  transaction — earlier valid rows in the same file are committed even if
  later rows fail. Acceptable for a demo bulk-load tool; a production import
  pipeline should probably support dry-run/validate-then-commit.
- **Rate limiting, request size limits, and WAF-style protections** are not
  implemented — this is meant to run behind a reverse proxy/API gateway in
  any real deployment, not to be internet-facing on its own.
- **Docker Desktop image-store issues** were encountered during development
  on macOS (unrelated to this project's Dockerfiles/compose config — see
  `docs/runbook.md` for the workaround and how the full stack was instead
  verified against local Postgres/Redis processes). The `docker-compose.yml`
  and Dockerfiles are structurally correct and were used successfully
  earlier in development to bring up Postgres/Redis; a clean environment
  should not hit this.

## No production claims

Nothing in this repository, its README, or its documentation should be read
as a claim that ControlFlow is used in, or suitable for, production
operations at any organization. It is a demonstration of engineering
practice on synthetic data.
